# PR レビューの実験 v2（やり直しの設計）

2026-10-04 の PR 単位のレビューの実験（[結果](../results/2026-10-04-auto-review/README.md)・[3 回ずつの結果](../results/2026-10-04-auto-review-repeat/README.md)）を、
公平な条件でやり直すための設計です。**この文書の段階では、モデルは 1 回も呼んでいません。** 実際に流すか（費用をかけるか）は人が決めます。

## 1. なぜやり直すか（v1 の問題）

| v1 の問題 | 何が起きたか | v2 での対策 |
|---|---|---|
| 答えが差分に漏れていた | バグを戻すときに、説明のコメントやテストを消した。消した行（`-` の行）に「同時に登録されたら…」のような答えそのものが書いてあった | コメントとテストは消さない。漏れの検査（`bench/prs_v2/leak_check.py`）を通らない課題は作れない |
| 採点がキーワードの一致 | 1 文字のキーワードでも「当たり」になり、説明が誤っていても検出に数えた | 人が目隠しで、指摘を 1 件ずつ「正しい・一部正しい・誤り」で採点する |
| 同じ AI が全部作った | バグ・課題・採点を同じ AI が作り、答えの書き方とモデルの言い回しが似やすかった | 採点は人が行う。課題（`spec.yaml`）と答えも、流す前に人が読んで確かめる（7 章） |
| PR の ID が種類を表した | `P01`（バグ）・`N01`（問題なし）・`D01`（おとり） | ID は `T01`〜 で、決まった乱数で並べ替える。種類は `answers.yaml` にだけ書く |
| 1 回だけ・11 PR | ばらつきが分からず、差があるのか偶然かを言えなかった | 33 PR × 3 回。PR を単位にしたブートストラップで信頼区間を出す |
| 費用を `claude -p` で測った | キャッシュ・思考のトークンが混じり、API で直接呼ぶときと条件が違った | API で直接呼ぶ（`--backend anthropic`）。見積もりも API の料金表で出す |

## 2. 確かめたいこと（仮説）

比べる構成は 3 つです（Haiku は v1 で全体のレビューに向かないと分かったので外す）。

| 構成 | 中身 |
|---|---|
| `standard` | Sonnet だけで 1 回 |
| `deep` | Opus だけで 1 回 |
| `auto` | auto-review の振り分け（ふだん Sonnet 1 回。危ない PR と、Sonnet が MUST を出したときだけ Opus が検証） |

| 仮説 | 中身 | 何で判断するか |
|---|---|---|
| H1 検出 | `deep` は `standard` より不具合を多く見つける | 検出率（ゆるめ）の差 `deep − standard` の 95% 区間が 0 より上 |
| H2 誤った MUST | `deep` は `standard` より、正しい PR（おとり・問題なし）で誤った MUST を出しにくい | 「誤った MUST を 1 件でも出した実行の割合」の差の区間が 0 より下 |
| H3 auto ≒ deep | `auto` の検出は `deep` とほぼ同じで、誤った MUST も多くない | 検出率の差 `auto − deep` の区間の下限が −10 ポイントより上（同等とみなす幅）、誤った MUST の差の区間の上限が 0.1 / PR 以下 |
| H4 費用 | `auto` の 1 PR あたりの費用は `deep` より安い | 実測の費用（1 PR あたり）の差の区間が 0 より下 |

あわせて、重要度の付け方（答えの重要度に合うか、採点者が「適切」としたか）と、正しい指摘の割合（ノイズの少なさ）も見ます。

## 3. 課題の作り方（bench/prs_v2）

dev-environment の sample-app の `main`（修正済み. コミット `49d093f`）に、小さな変更を当てた PR を 33 件作りました。
作り方は `bench/prs_v2/spec.yaml`（答えを含む元データ）→ `make_prs_v2.py` → `tasks/T??.diff`（モデルに渡す差分）・`cases.yaml`（題名と説明）・`answers.yaml`（答え）です。

### 決まり

1. **コメントとテストを消さない。** 足すのはよい。消した行に答えが出るのを防ぐ（漏れの検査が `-` の行のコメント・テストを見つけたら失敗）
2. **関係のない小さな変更（noise）を混ぜる。** Javadoc の追加・変数名の変更・手順書の言い回し・テストの追加など、動きを変えない変更を 1〜3 個。
   **同じ noise を、バグの PR・問題の無い PR・おとりの PR のどれにも使う**（noise の有無や種類で見分けられないように. テストで確かめる）
3. **バグの場所を散らす。** 17 件のバグは 12 ファイル・5 種類（Java・MyBatis の XML・`application.yml`・`messages.properties`・`build.gradle`）
4. **答えの語を差分・題名・説明に書かない。** 題名と説明は「作者が何をしたつもりか」だけ。不具合の説明（例: 「大文字小文字」「文字化け」）は答えの `leak_terms` に書き、検査で探す
5. **ID と並び順から種類が分からないようにする。** `T01`〜 を乱数（`seed`）で振る。`cases.yaml` には題名と説明しか書かない
6. 不具合は「よく読めば分かるが、差分だけでは目立たない」ものを中心にし、易しいもの（すぐ上のコメントと食い違う）から難しいもの（差分に無い DB の定義と食い違う）まで混ぜる

### 内訳

| 種類 | 件数 | 中身 |
|---|---|---|
| バグ（bug） | 17 | 1 PR に不具合 1 つ。答えに場所（ファイル・行）・正しい重要度（と許す範囲）・正確な説明がある |
| 問題なし（clean） | 8 | テストの追加・文書・名前の変更・定数への置き換え |
| おとり（decoy） | 8 | 危なそうに見えるが正しい変更（文字コードの指定を省く・例外の捕捉を絞る・SQL の競合の対象を制約名にする など）。答えに「なぜ正しいか」がある |

バグの例（答えの詳しい説明は `answers.yaml`）: 数量の上限の比較、取込のエラーの行の数え方、メールアドレスの保存の値、500 の応答の中身、ジョブ ID の誤りの終了コード、
引数の確認、S3 の読み込み、SQL の値の並び、入力チェックの上限と DB の定義、ID の型、列数の確認、空白の扱い、S3 の接続先の判定、MyBatis の XML の場所、
コンパイルの対象の版、トランザクションの指定、メッセージの埋め込み。

### 漏れの検査（`bench/prs_v2/leak_check.py`）

`auto-review/tests/test_prompt_leak.py` の考え方（答えの側から禁止する語と文を作る）を、差分と題名・説明にも広げたものです。

- 形: コメントの行・テストのファイルの行・ファイルそのものを消していない
- 語: 答えの `leak_terms` が差分の `+`/`-` の行・題名・説明に無い（英数字の語は単語の境界で探す）
- 文: 答えの説明と同じ 10 文字の並び（日本語を 3 文字以上含むもの. コードの断片は差分にあって当然なので除く）が無い。題名・説明が答えの文と似ていない
- 公開する情報: ID が `T` + 数字、題名・説明に「おとり」「不具合」などが無い、`cases.yaml` に種類が書いていない
- プロンプト: auto-review・reviewers・examples のプロンプトに答えの語・文が無い

`make_prs_v2.py` は最後にこの検査を行い、漏れがあれば失敗します。CI でも `runner/tests/test_prs_v2.py` が確かめます。

### 残る弱さ

- 課題と答えは、v1 と同じく AI が書いた。採点を人にしても、「AI が思いつく不具合」に偏っている可能性は残る → 7 章の確認と、できれば人が書いたバグを数件足す
- バグの PR は必ず 2 ファイル以上を変える（noise を混ぜるため）。問題なし・おとりには 1 ファイルだけの PR もある。モデルは PR を 1 件ずつ見るので比べられないが、完全に同じ分布ではない
- 答え（`answers.yaml`）は公開リポジトリにある。API で差分だけを渡す限りモデルからは見えないが、ウェブを検索できるエージェントで流すときは使えない
- 1 PR に不具合 1 つで、実際の PR より見つけやすい

## 4. 標本の大きさと繰り返し

- 33 PR（バグ 17・問題なし 8・おとり 8）× 3 構成 × **3 回** = 297 回の実行
- 3 回流すのは、同じ PR でも結果が揺れるため（v1 の 3 回ずつの結果で、同じ PR・同じ構成でも MUST の有無が変わった）
- 区間は PR を単位に出す（同じ PR の 3 回は独立ではないので、まとめて抽出する）。種類ごとに抽出する（層別）
- **見分けられる差の目安**: バグの PR が 17 件なので、検出率の区間の幅は ±15〜20 ポイント程度になる見込み。構成の差は同じ PR で対にして比べるので幅は狭くなるが、
  **差が 15 ポイントより小さいと「差は見えなかった」としか言えない**。結論が出なければ、バグの PR を 40 件程度に増やして流し直す（費用は 7 章の見積もりのほぼ比例）

## 5. 流し方

```bash
# 0) 課題を作り直す（spec.yaml を変えたときだけ. dev-environment は読むだけ）
python bench/prs_v2/make_prs_v2.py ../dev-environment

# 1) 費用の見積もり（モデルは呼ばない）
python runner/pr_bench.py ../dev-environment --bench bench/prs_v2 --configs standard,deep,auto --repeat 3 --estimate-only

# 2) 実行（★費用がかかる。人が決めてから。ANTHROPIC_API_KEY が要る）
python runner/pr_bench.py ../dev-environment results/<日付>-v2 --bench bench/prs_v2 --configs standard,deep,auto \
    --repeat 3 --backend anthropic --yes --workers 4

# 3) 目隠しの採点表を作る（鍵は採点する人に渡さない場所へ）
python runner/blind_sheet.py results/<日付>-v2 --bench bench/prs_v2 \
    --sheet scoring/sheet.csv --xlsx scoring/sheet.xlsx --key ~/secret/key.json

# 4) 人が採点する（6 章）

# 5) 鍵と合わせて集計する
python runner/blind_score.py scoring/sheet.xlsx ~/secret/key.json --bench bench/prs_v2 --out results/<日付>-v2/blind.md
```

- 実行は API で直接呼ぶ（`--backend anthropic`）。`claude -p` は使わない（キャッシュ・思考のトークンで条件が変わるため）
- 変更後のファイルの全文も渡す（`--diff-only` を付けない）。auto-review を実際に使うときと同じ条件
- `router.yaml` とプロンプトは、流した時点のコミット SHA を結果の README に書く。途中で変えない
- 流す前に、`ANTHROPIC_API_KEY` のワークスペースに月の上限（例: $30）を掛けておく

## 6. 目隠しの採点

### 誰が・何を見るか

- 採点する人は、**どの指摘がどのモデル・構成から出たかを知らない**状態で採点する。`blind_sheet.py` の表には、モデル名・構成・何回目か・検証の状態（検証済み・要確認）を出さない
- 指摘の順番は乱数で混ぜる。同じ PR に同じ中身の指摘が複数の実行から出たら 1 行にまとめる（どこから出たかは鍵にだけ残る）
- 鍵（`key.json`）は採点が終わるまで採点する人に渡さない。実行した人と採点する人を分けられるなら分ける。採点する人は `results/` の生の結果を開かない
- 表には PR の題名・種類・答えの説明が入る（`--no-answers` で空にできる）。答えを見ずに 1 回目を採点したいときは `--no-answers` で作る

### 基準（指摘 1 件ごと）

| 列 | 値 | 意味 |
|---|---|---|
| verdict | `correct` | 本当の問題で、場所と理由の説明が正しい（答えの不具合でなくても、本物の問題なら correct） |
| | `partial` | 場所や問題には当たっているが、理由が不正確・あいまい、または影響を大きく取り違えている |
| | `incorrect` | 問題ではない・誤った説明・推測だけで根拠が無い（おとりの「正しい理由」に反する指摘はここ） |
| hits_key | `yes` / `no` | 答えの不具合を指しているか（`incorrect` なら必ず `no`） |
| severity_fit | `ok` / `high` / `low` | 付いている重要度（MUST・WANT・NITS・Q）が中身に見合うか。MUST は「直さないと壊れる・危ない」 |
| note | 自由 | 迷った理由など |

- 迷ったら厳しいほう（`partial` より `incorrect`、`correct` より `partial`）にし、note に理由を書く
- 日本語（○・△・×、はい・いいえ、適切・重すぎ・軽すぎ）でも読める
- 量の目安: v1 では 1 実行あたり指摘 2.6〜3.1 件だったので、297 実行で **800〜900 行**。1 行 1 分なら 15 時間前後。2 人で分けるなら、
  一部（例: 100 行）を 2 人とも採点し、一致の割合を結果に書く（一致が 8 割未満なら基準を直して採点し直す）

### 集計（`blind_score.py`）

| 指標 | 数え方 |
|---|---|
| 検出率（厳しめ / ゆるめ） | バグの PR の実行のうち、`hits_key=yes` で `correct`（ゆるめは `partial` も）の指摘がある割合 |
| 誤った MUST / PR | MUST で `incorrect` の件数 ÷ 実行数。おとり・問題なしの PR で 1 件でも出した実行の割合も出す |
| 正しい指摘の割合 | (`correct` + 0.5 × `partial`) ÷ 見せた指摘 |
| 重要度 | 答えに当たった指摘の重要度が答えの `severity_ok` に入る割合（自動）と、`severity_fit=ok` の割合（採点者） |
| 費用 / PR | 実行の結果に残る実測の費用 |

信頼区間は、PR を種類ごとに復元抽出するブートストラップ（2,000 回）の 95% 区間です。構成の差（`deep − standard` など）も同じ抽出で対にして区間を出します。
指摘 0 件の実行も分母に入れます（鍵に全実行を残しているため）。

## 7. 費用の見積もり

`pr_bench.py --estimate-only` の結果です（モデルは呼んでいません）。単価は devtools-common の料金表（`devtools_common.llm.PRICES`. 2026-10-06 確認）で、API で直接呼ぶ場合です。

| 構成 | 実行数 | 入力トークン | 出力トークン（見込み） | **費用の見込み** | 上限（出力がすべて max_tokens） | 1 PR あたり |
|---|---|---|---|---|---|---|
| standard（Sonnet 1 回） | 99 | 0.28 M | 0.094 M | **$1.51** | $4.53 | $0.015 |
| deep（Opus 1 回） | 99 | 0.28 M | 0.154 M | **$4.22** | $9.05 | $0.043 |
| auto | 99 | 0.43 M | 0.148 M | **$3.16**（$1.75〜$4.49） | $11.67 | $0.032 |
| 合計 | 297 | | | **$8.88** | $25.25 | |

- 入力トークンは、実際に渡すプロンプト（差分 + 変更後のファイルの全文 + システムプロンプト）の ASCII の文字数 ÷ 3（`router.yaml` の `chars_per_token`）+ 日本語など ASCII 以外の文字数（1 文字 1 トークン。`auto_review.tokens`）
- 出力トークンの見込みは、2026-10-04 の実測の平均（段階・モデルごと）。上限は `router.yaml` の `max_tokens` をすべて使い切った場合
- auto は、Sonnet が MUST を出して Opus の検証に回る割合しだいで変わる。見込みは v1 の実測の 51%、幅は 0%〜100%。振り分けは deep 2 件・skip 1 件（文書だけの PR）・standard 30 件
- プロンプトのキャッシュは使わない前提、再試行の分は含まない。**予算は $30 を上限に見ておけば足りる**
- 採点の人手（6 章. 15 時間前後）のほうが、API の費用よりずっと大きい

## 8. 結果ごとの判断

| 結果 | 判断 |
|---|---|
| H1・H2 とも成り立つ（deep が検出で上、誤った MUST で下. 区間が 0 をまたがない） | 今の推奨「まず Opus 1 回」を、根拠付きで維持する |
| deep と standard の差が見えない（区間が 0 をまたぐ） | 費用の安い **Sonnet 1 回** を既定にし、MUST は人が根拠を確かめる運用にする。結論を急がないなら、バグの PR を増やして流し直す |
| H3 が成り立ち（auto ≒ deep）、H4 も成り立つ（auto が安い） | **auto を既定にする**。そのうえで本物の PR で「Sonnet が MUST を出す割合」を測り、見積もりどおり安くなるかを確かめる |
| H3 が成り立たない（auto の検出が deep より明らかに低い） | auto はやめ、Opus 1 回（費用が気になるなら Sonnet 1 回）にする。振り分けの規則（`router.yaml`）を見直すなら、別の課題で確かめる |
| H3 は成り立つが H4 が成り立たない（auto が安くない） | 精度が同じで安くないなら、仕組みの単純な Opus 1 回にする |
| どの構成も誤った MUST が多い（例: 0.3 件 / PR 以上） | モデルを選ぶ前に、プロンプトの重要度の基準（MUST の意味）を見直し、同じ課題で流し直す |
| どの構成も検出率が低い（例: ゆるめで 50% 未満） | 課題が文脈なしでは解けない可能性。渡す文脈（DB の定義・設定ファイル）を増やす案を、別の実験として試す |
| 採点者どうしの一致が低い（8 割未満） | 結果は使わない。基準を直して採点し直す |

どの場合も、結果の README には「言えること」と「まだ言えないこと」を分けて書き、区間をそのまま載せます（v1 の点検で、言い過ぎを指摘されたため）。

## 9. 流す前に人が確かめること

- [ ] `answers.yaml` のバグ 17 件が、本当に不具合で、説明と重要度が妥当か（特に severity_ok の幅）
- [ ] おとり 8 件が、本当に正しい変更か（`why_correct` に納得できるか）
- [ ] 問題なしの 8 件に、気づかない不具合が混ざっていないか
- [ ] 差分を数件読み、答えが推測できる書き方になっていないか（検査で見つからない漏れ）
- [ ] 費用の見積もり（7 章）と上限の設定
