# agent-lab 設計メモ

> 状態: たたき台（2026-10-04）。実装前に方針と実験計画をそろえるためのメモです。

## 1. 目的

AI エージェントに **どこまで任せられるか** を、つなぐ道具（MCP）・任せる範囲（自律度）・確かめ方（マルチモデル・マルチエージェントの相互レビュー）の 3 つの軸で実験し、
**数字で比べられる形** で残す。結果は ai-coding（開発プロセス）と社内展開の判断材料にする。

やらないこと:
- 本番環境・実案件のデータに触れる実験（すべて sample-app と架空のデータで行う）
- 特定の製品の宣伝・比較記事（結果は条件と数字だけを書く）

## 2. 3 つの軸

### 2.1 MCP: 道具をつなぐ

| 段階 | つなぐもの | 狙い |
|---|---|---|
| M1 | **自作ツールの MCP サーバー**（doc2md・design-diff・fieldcheck・qa・spec-trace） | すでに JSON 出力と終了コードがそろっているので、薄く包むだけで「エージェントの道具」になる |
| M2 | GitHub（PR・Issue・CI の結果） | 「PR を出す → CI の失敗を読む → 直す」をエージェントが自分で回す |
| M3 | ローカルの DB（読み取り専用）・ブラウザ操作 | sample-app のデータと画面を見ながらテスト・調査する |
| M4 | 課題管理・チャット（Backlog・Slack など） | 課題から作業を始め、結果を報告する。公式の MCP サーバーの有無と社内の利用可否を確認してから |

自作 MCP サーバーの方針:
- 1 ツール = 1 MCP ツール。引数は各 CLI の引数そのまま、結果は CLI の JSON レポートをそのまま返す
- 書き込みを伴うもの（office-replace の実行、Backlog・Slack への送信）は M1 では入れない。入れるときは「試行（dry-run）→ 人の承認 → 実行」の 2 段にする
- stdio で動かす（ローカルで完結。ネットワークのポートを開けない）

### 2.2 自律度: どこまで任せるか

「制限を外す」とは、任せる範囲を広げる代わりに **壊れても困らない場所で動かす** こと。段階を決めて 1 段ずつ上げる。

| レベル | エージェントにできること | 人がすること | 前提 |
|---|---|---|---|
| L0 | 提案だけ（コードは書かない） | すべて | – |
| L1 | ローカルでファイルを編集、テストを実行 | 変更を見てコミット | 作業ツリーだけ。ネットワークなし |
| L2 | ブランチを作って PR まで | レビューしてマージ | 使い捨ての環境・CI のゲート |
| L3 | CI が通れば自動マージ（決めた種類の変更だけ） | 事後に確認・差し戻し | ゲートの網羅性を測ってから |
| L4 | 課題の起票から完了報告まで | 方針と例外の判断 | L3 の実績と監査ログ |

どのレベルでも守る土台:
- **使い捨ての実行環境**（devcontainer やクラウドのサンドボックス）。本番の認証情報は渡さない
- **外向きの通信は許可したものだけ**（パッケージのレジストリ・GitHub など）
- **危険な操作を事前に止める**（hooks: `rm -rf`、強制 push、秘密情報らしき文字列の書き込み、ゲートの設定の変更）
- **すべての変更は PR 経由**、エージェントの操作ログを残す
- **費用の上限**（1 タスクあたりのトークン・時間）を決め、超えたら止めて人に返す
- ai-coding のルール（自動修正は 3 回まで、ゲートを甘くする変更は禁止）をそのまま使う

### 2.3 相互レビュー: どう確かめるか

| 構成 | 内容 | 仮説 |
|---|---|---|
| R0 | 書いたエージェント自身が見直す | 同じ見落としを繰り返しやすい（基準） |
| R1 | 同じモデルの別エージェントがレビュー | R0 より少し良い |
| R2 | **別のモデル**がレビュー | 見落としの傾向が違うので、R1 より多く見つける |
| R3 | 観点ごとに役割を分けた複数のレビュー（設計整合・例外処理・セキュリティ・テスト） | 観点の漏れが減る。ノイズの指摘も増える |
| R4 | R3 の結果を突き合わせ、**意見が割れたものだけ人に回す** | 人のレビュー時間を減らしつつ、見落としを増やさない |

指摘の書式は既存のもの（MUST / WANT / NITS / Q、根拠、無効となるケースの確認）にそろえ、quality-analytics でそのまま集計できるようにする。

## 3. 実験のやり方

### 課題集（ベンチマーク）

- **仕込みバグ集**: sample-app にバグを 1 つずつ仕込んだブランチを用意する。最初は教材で見つかった弱いところ 8 件
  （同時登録の 500、1 行の誤りで全件ロールバック、終了コードの誤り など）から作り、20〜30 件に増やす
- **実装課題集**: 設計書（ai-coding の samples/design-docs 形式）から新しい API・バッチを作る課題 5〜10 件。正解のテストを別に持つ
- 課題ごとに「正解（見つけるべき指摘・通るべきテスト）」を YAML で持つ

### 測るもの

| 指標 | 意味 |
|---|---|
| 検出率 | 仕込んだバグのうち、レビューで見つけた割合 |
| ノイズ率 | 指摘のうち、正解に関係しない・表記や好みの割合（quality-analytics の B） |
| 完了率 | 実装課題で、正解のテストがすべて通った割合 |
| 人の介入回数 | 人に返った回数（ゲートの失敗が 3 回、判断が必要、など） |
| 費用と時間 | 1 課題あたりのトークン・費用・経過時間 |

同じ課題・同じ条件で、構成（R0〜R4、L1〜L3、MCP の有無）だけを変えて比べる。モデルや版を変えたときに同じ課題集を流し直し、劣化を見る（回帰テスト）。

## 4. リポジトリの構成（案）

```text
agent-lab/
├── docs/DESIGN.md          このメモ
├── mcp-server/             自作ツールの MCP サーバー（M1）
├── sandbox/                使い捨ての実行環境（devcontainer）と hooks・通信の許可リスト
├── reviewers/              レビュー役の定義（役割・観点・指摘の書式）と構成 R0〜R4
├── bench/
│   ├── bugs/               仕込みバグの課題（ブランチ名・正解の指摘）
│   └── tasks/              実装課題（設計書・正解のテスト）
├── runner/                 課題を構成ごとに流して結果を集める
└── results/                実験結果（条件・数字・所感）。生のログは残さない
```

## 5. 進め方

| 段階 | やること | 終わりの目安 |
|---|---|---|
| 1 | MCP サーバー（M1）と仕込みバグ 8 件 | Copilot / Claude から自作ツールを呼べる。課題を手で流せる |
| 2 | runner と R0〜R2 の比較 | 別モデルのレビューで検出率がどう変わるか、数字が出る |
| 3 | サンドボックスと L1〜L2 | エージェントが PR まで作り、CI の失敗を自分で直す |
| 4 | R3・R4 と L3 の試行 | 人のレビュー時間と見落としのバランスが見える |
| 5 | 結果を ai-coding のガイドラインと社内提案に反映 | 「この種類の変更はここまで任せてよい」が決まる |

## 6. 決めること・確認すること

- 使うモデルとその契約（どれを書き手・レビュー役にするか、費用の上限）
- エージェントの実行環境（ローカルの devcontainer か、クラウドのサンドボックスか）
- 社内の AI 基盤（閉域の Azure 環境）とつなぐか: つなぐなら、MCP サーバーとモデルの呼び出しを閉域の中で動かす
- 結果の公開範囲（個人の公開リポジトリには条件と数字だけ。社内の情報は入れない）
