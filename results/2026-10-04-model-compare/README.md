# 2026-10-04 モデルの大きさによるレビューの違い（R1 の予備実験）

## 条件

| 項目 | 内容 |
|---|---|
| 対象 | dev-environment の sample-app（ソース・テスト・設定・SQL・build.gradle） |
| 仕様 | ai-coding/samples/design-docs の設計書 2 本 |
| プロンプト | [reviewers/code-review.prompt.md](../../reviewers/code-review.prompt.md)（3 モデルで同じ） |
| モデル | Claude Haiku 4.5 / Sonnet / Opus（Claude Code のサブエージェントとして実行。答えのある資料は読まない指示） |
| 回数 | 各 1 回（ばらつきは未測定） |
| 正解 | [bench/bugs/sample-app-known.yaml](../../bench/bugs/sample-app-known.yaml)（8 件） |

## 結果

| モデル | 指摘数 | 検出（自動） | 検出（目視で補正） | 見逃し（補正後） |
|---|---|---|---|---|
| Haiku | 6 | 2 / 8 | 1 / 8 | B02〜B08 |
| Sonnet | 20 | 6 / 8 | 6 / 8 | B04, B07 |
| Opus | 19 | 7 / 8 | 6.5 / 8 | B07（B04 は原因の取り違えで半分） |
| 3 つの和 | 45 | 7 / 8 | 7 / 8 | B07 |

目視での補正:
- Haiku の B08 は「メッセージを properties から読んでいない」という別の指摘で、メッセージ ID の欠落ではないので外した
- Opus の B04 は「baseUrl を付け忘れると null」としており、本当の原因（付けても Gradle がテストに渡さない）を取り違えているので半分とした
- B02 と B03（外部キー違反・桁あふれで全件ロールバック）は、Sonnet・Opus とも 1 つの指摘にまとめていた。正解の分け方が細かすぎる可能性がある

## 分かったこと

- **小さいモデルは指摘の数も検出も少ない**。Haiku は 6 件しか出さず、同時登録（B01）以外の重要な弱点を見逃した。レビュー役に軽いモデルを使うのは、この課題では不向き
- **Sonnet と Opus の差は小さい**（6 対 6.5）。ただし Opus は根拠の行番号・再現手順が具体的で、人が確かめる手間が少ない
- **3 つを合わせても B07（404 のメッセージで ID が「1,234」になる）は誰も見つけなかった**。ライブラリの細かい挙動（MessageFormat の桁区切り）は、モデルを増やしても見つかりにくい。テスト（ID 1234 で確かめる）で押さえるべき種類
- 正解に無い指摘（ノイズ率 53〜67%）には本物の問題も含まれる。例: Sonnet の「設計書は大文字小文字を区別しない重複チェックだが、SQL は完全一致」（要確認）。正解集を育てる材料にする

## 限界と次にやること

- 1 回ずつの結果なので、同じ条件で 3〜5 回流してばらつきを見る
- 同じ会社のモデルの大きさ違いで、**別の会社のモデル**との比較（R2 の本題）はまだ。Copilot のモデル切り替えや Azure の環境で行う
- 自動採点はキーワードの一致なので、目視の補正が要る。LLM に採点させる方法（採点役のモデル）も試す
- 次は R3（観点ごとに役割を分けたレビュー）を同じ課題で比べる
