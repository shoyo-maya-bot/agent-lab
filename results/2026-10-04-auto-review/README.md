# 2026-10-04 PR 単位のレビュー: 1 モデル・上位モデル・自動の振り分け（auto）の比較

> **注意（2026-10-04 追記）**: この実験の課題は、消したコメントやテスト名にバグの説明が書いてあり、答えが差分に漏れていました。
> 「どのモデルも 8/8」はレビューの力を測れていません。また「auto は Opus と同じ精度で安い」は [2 回目](../2026-10-04-auto-review-repeat/README.md) で再現しませんでした。
> 言える範囲は [auto-review の README](../../auto-review/README.md) の「言えること・まだ言えないこと」を参照してください。

## 条件

| 採点 | [runner/pr_bench.py](../../runner/pr_bench.py)。正解の判定は [score.py](../../runner/score.py) と同じキーワードの一致 |

## 分かったこと

- **PR 単位なら、どのモデルも仕込んだ弱いところを見つける**（8 / 8）。リポジトリ全体を見た[前回の実験](../2026-10-04-model-compare/README.md)では Haiku は 1 / 8 だった。差分が小さく、問題がその中にあるため
- **モデルの差は「誤った MUST」に出る**（Haiku 4、Sonnet 2、Opus 1）。人が確かめる手間はここで増える
- **auto は Opus と同じ精度（誤った MUST 1）を、Opus を毎回呼ぶより安く出した**。Opus の範囲を「Sonnet の MUST」と「危ないファイル」に絞っているため
- この課題は 11 PR 中 8 PR に弱いところを仕込んだので、Opus に上がりやすい。**実際の PR は MUST が出る割合が低いので、auto の費用は Sonnet だけの場合に近づく**（MUST が出る PR が 2 割なら 1 PR あたり約 $0.035 の見込み）
- **問題の無い PR では、どの構成も MUST・WANT を出さなかった**。文書だけの PR は auto が省いた
- どの構成も **費用は 1 PR あたり数セント**。費用より、人が読む指摘の数と正確さで構成を選ぶべき
- B04（Karate の接続先）・B08（ログのメッセージ ID）の重要度は正解と違った（MUST と言いすぎ・WANT）。重要度の基準はプロンプトで調整の余地がある

## 限界と次にやること

- 各 1 回。同じ条件で 3〜5 回流してばらつきを見る
- 弱いところは 1 PR に 1 つだけで、PR の説明も短い。実際の PR（複数の変更が混ざる・説明が長い）に近い課題を足す
- Opus の検証で「却下」は 0 件だった（Sonnet の MUST が本物だったため）。**誤った MUST を含む課題** を作り、却下できるかを確かめる
- Haiku は `claude -p` の既定で思考のトークンが多く出たため、Sonnet より高く・遅く出た。API で思考を切った条件でも比べる
- 振り分けの点数（deep にする 6 点）は、この課題だけで決めた。実際の PR の履歴（quality-analytics の指摘の傾向）で見直す
