# 2026-10-04（2 回目）auto-review: 3 回ずつ流したばらつきと、誤った MUST を却下できるか

[1 回目](../2026-10-04-auto-review/README.md) で残した「各 1 回」「却下が 0 件」の 2 点を確かめた。

## 条件（1 回目からの変更点）

| 項目 | 内容 |
|---|---|
| 課題 | 1 回目の 11 PR（P01〜P08・N01〜N03）に、**おとりの PR 5 件（D01〜D05）** を足した 16 PR。おとりは危なそうに見えるが正しい変更で、MUST は誤り（[cases.yaml](../../bench/prs/cases.yaml) の `why_correct`） |
| 構成 | standard（Sonnet だけ）/ deep（Opus だけ）/ auto |
| 回数 | 各 **3 回**（16 PR × 3 構成 × 3 回） |
| auto の修正 | 検証役が「決められない」とした指摘を、合流のときに「検証済み」に上げてしまう不具合を直し（`uncertain` → 表示は「要確認」）、auto だけ流し直した |

## 結果

| 構成 | 検出（P01〜P08 × 3 回） | 1 PR あたりの指摘 | 誤警報 MUST・WANT（N01〜N03 × 3 回） | 1 PR あたりの費用 | 1 PR あたりの時間 |
|---|---|---|---|---|---|
| standard（Sonnet） | 24 / 24 | 2.6 | 3 | $0.018 | 10 秒 |
| deep（Opus） | 24 / 24 | 3.1 | 0 | $0.044 | 18 秒 |
| auto | 24 / 24 | 2.8 | 2 | $0.048（この課題での値。下の見込みを参照） | 17 秒 |

おとりの PR（D01〜D05 × 3 回 = 15 回）:

| 構成 | MUST を出した回 | 人に見せた MUST | うち「検証済み」 | うち「要確認」 | 検証で却下 |
|---|---|---|---|---|---|
| standard | 3 | 4（すべて未検証のまま） | 0 | 0 | 0 |
| deep | 0 | 0 | 0 | 0 | 0 |
| **auto** | Sonnet が 4 件出した | 2 | **0** | 2 | 2 |

Sonnet が出した誤った MUST はすべて D01（重複確認を DB の一意制約に一本化）で、「一意制約が実在するか差分から見えない」「PostgreSQL のトランザクションが失敗状態になりうる」という推測の指摘だった。
auto では Opus が 2 件を却下し（変更前から同じ前提・同じ処理だった）、2 件を「要確認」（DDL を見ないと決められない）にした。**「検証済み」の MUST として人に見せた誤りは 0 件**。

## 分かったこと

- **ばらつき**: 3 回とも、どの構成も仕込んだ弱いところを全部見つけた（24 / 24）。PR 単位の検出は安定している
- **誤った MUST**: Sonnet だけだと、おとり 15 回のうち 3 回で誤った MUST が出る（すべて「推測」に基づくもの）。auto は Opus の検証で、それを「却下」か「要確認」に振り分けた。Opus だけなら最初から出なかった
- **費用は「MUST が出る PR の割合」で決まる**。auto の内訳は次のとおり

| auto の PR | 回数 | 1 PR あたり |
|---|---|---|
| Sonnet だけで終わった（MUST なし） | 19 | $0.009 |
| Opus の検証まで進んだ | 26 | $0.083 |

  この課題は 16 PR 中 8 PR に弱いところを仕込んだので、Opus まで進む割合が高い（26 / 45）。実際の PR で Sonnet が MUST を出す割合が 2 割なら 1 PR あたり約 $0.024、1 割なら約 $0.016 の見込み（Opus だけは $0.044、Sonnet だけは $0.018）
- **Opus の検証 1 回（$0.07 前後）は、Opus のレビュー 1 回（$0.044）より高い**。検証の入力に一次の指摘と重点ファイルを足し、出力に判定の理由を書かせているため。MUST の多い PR が続くチームでは、auto より Opus だけのほうが安くなる

## どう使い分けるか

| 状況 | おすすめ |
|---|---|
| PR の多くは小さく、MUST が出るのは 2 割以下 | **auto**（費用は Opus だけの約半分、誤った MUST は「要確認」か「却下」に回る） |
| 危ない変更が多い・費用より手間を減らしたい | **Opus だけ**（この課題では誤った MUST・誤警報とも 0） |
| 費用を最小にしたい | Sonnet だけ。ただし誤った MUST が 2 割ほど混じる前提で、人が根拠を確かめる |

## 限界と次にやること

- おとりは 5 件で、誤った MUST が出たのは D01 だけ。おとりを増やす（権限・SQL・非同期など）
- Opus の検証の費用を下げる: 検証の入力を MUST の箇所の前後に絞る、出力の上限を下げる
- 誤警報（N01〜N03）はすべて N01（テスト追加）への WANT で、「下限と上限の拒否のテストが対になっていない」という提案だった。誤りというより好みに近く、MUST は 0
